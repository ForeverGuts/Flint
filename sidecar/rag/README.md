# rag-sidecar —— flint 的「查我的笔记」侧车（MCP server）

flint 本体保持零运行时依赖；RAG 全部住在这个 Python 侧车里。2026-10-06 起
侧车以 **MCP server** 形态暴露检索（`mcp_server.py`，纯标准库，零新增依赖），
flint 经 `src/mcp/client.ts` 作为 MCP client 长驻连接调用；私有 CLI（query.py）
保留为手测与降级路径。任何其他 MCP 客户端也可直接接入本 server。

## 架构：一条进程边界，两套调用形状

```
              flint 进程（TypeScript · package.json 的 dependencies 为空）
   ┌──────────────────────────────────────────────────────────────┐
   │  Agent Loop ─→ ToolRegistry ─→ note_search（21 个内置工具之一）│
   │                                      │                       │
   │                   MCP 主通道 ┌───────┴────────┐ 降级通道      │
   │                              ▼                ▼              │
   │                   src/mcp/client.ts    child_process.spawn    │
   │                   （长驻连接 / 自愈）    （一把一 spawn）      │
   └──────────────────────────────┬────────────────┬───────────────┘
                                  │ stdio JSON-RPC │ argv 进 / stdout 出 JSON
                                  │     2.0        │
   ┌──────────────────────────────▼────────────────▼───────────────┐
   │           rag-sidecar 进程（Python · 独立 venv · 不进本体依赖）│
   │  mcp_server.py   协议层：initialize / tools/list / tools/call  │
   │  query.py        检索：改写 → 双路召回(BM25 + 向量) → RRF 融合  │
   │                        → 精排 → 单篇去重 → top-k               │
   │  index_build.py  索引：增量(签名) / 先删后插治孤儿 / 陈旧检测    │
   │                        / 检索前自动重建（三道闸）               │
   │  glossary.py     词典三层：内置 + 本地(热更新) + 候选池(人审)   │
   └──────┬───────────────────────────────────────────┬────────────┘
          │ 离线：读（只读）                           │ 在线：调嵌入 / 精排
   ┌──────▼──────────────┐                   ┌────────▼────────────┐
   │ Obsidian vault       │                   │ 硅基流动（免费档）    │
   │ 自建域 278 篇笔记     │                   │ bge-m3 / bge-reranker │
   └──────┬──────────────┘                   └─────────────────────┘
          └──→ .flint/rag-index/（Chroma 本地派生缓存；vault 全程只读，可随时重建）
```

**为什么要两张形状**：MCP 是正式路径（长驻、协议化、可被任意 MCP 客户端复用）；私有 CLI 是手测与
**兜底**——MCP server 起不来时 `note_search` 自动降级到它，两条路产出**同形状**结果、共用同一份渲染。

## 口径

- 语料：vault 中**自建**知识笔记（manifest.json，黑名单见 config.py）
- 不入库：第三方 clone 资料（227 篇）、模板、工具配置、索引文件
- 发给嵌入 API 前对手机号/邮箱/密钥做脱敏（报告在 .flint/rag-index/redact-report.jsonl）

## 检索管线（查询改写 + 混合召回 + 精排）

```
口语查询 → Qwen2.5-72B 改写为书面变体（补术语 + 领域词典；失败退回原查询单路）
        → [检索前自动重建：发现索引过期先跑增量重建再搜（开关/阈值/节流/降级）]
        → 原查询：bge-m3 嵌入 ─→ Chroma 向量召回 20 条（语义通道）┐
                → BM25 关键词打分（字面通道）→ RRF 融合 = 主干序   ├→ 主干 + 变体新块
        → 变体：各跑双路召回，独有的新块追加在主干之后（补充不稀释）┘
        → [可选] 范围限定 scope/--in：召回时按路径前缀过滤（两条通道共用同一个判据）
        → bge-reranker 精排：原问句先打分，top1 ≥ REWRITE_GATE(0.60) 时变体
          不参与（改写闸）；否则多查询 max-over-queries 融合
        → 单篇多样性上限（每篇笔记最多 2 块）取 top_k
        → 精排失败自动降级为融合序（保底可用）
```

- **为什么要查询改写**（2026-10-06 实测）：口语化问法（"怎么让大模型少花点钱"）
  对诊断 8 问只中 3——口语与笔记书面语之间有词面鸿沟，混合检索的字面/语义
  两头都够不着。改写器补的就是这一半；7B 会跑偏（"少花点钱"→"训练成本"），
  72B 才稳定补对术语（免费档 + 1.6s，对比全链路可接受）。
- **变体为什么"只补充、不稀释"**：multi-query 融合的经典陷阱——变体多路命中的
  "平庸块"在 RRF 里累分，会反超原查询单路命中的"精准块"（"大模型流式输出"
  一问实测被变体的 SSE/生成器块挤出候选池；原查询加权 1.6 也压不住——两路
  1.0+1.0 ≈ 单路 1.6，数学上就是打平）。所以主干 = 原查询自己的融合序
  （与关闭改写时逐位一致），变体独有块追加在后，绝不改动主干顺序。
- **精排为什么用 max-over-queries**：改写召回的好结果会被原查询的 cross-encoder
  惩罚（"几个AI怎么组队干活"融合序第 1，单查询精排直接挤出前 5）——每个候选取
  各查询（原 + 变体）rerank 分的最大值。但 max 融合只在改写闸放行时启用（见上），
  原问句已命中的书面题不让变体掺和——两个机制是一对，分别守住"该救的救回"
  与"不该掺的不掺"。
- **为什么要检索前自动重建**（第 10 步，2026-10-06）：陈旧检测只提醒不代劳时，
  提醒常被无视，下一次检索继续拿旧结果。现在检索前发现 stale 就顺手跑增量重建
  （秒级、只重嵌变更块），搜到的永远是新索引。安全边界：重建只写 INDEX_DIR
  （笔记库之外的派生缓存），vault 全程只读——性质与浏览器刷新自己的缓存同类，
  不属于 flint 写闸管的"Agent 写用户文件"。风险由三道闸兜住：变更篇目超过
  `RAG_AUTO_REBUILD_MAX_FILES`（默认 50）不代劳、长驻进程内重建尝试（含失败）
  节流 30s、重建失败按过期索引继续搜。`RAG_AUTO_REBUILD=0` 退回只提醒。
- 增量核心提炼在 `index_build.incremental_rebuild()`：CLI 与自动重建共用同一段
  代码（不存在两套真相）；它**不打印**、`embed_all` 的进度只走 stderr——
  复用方可能活在 MCP server 进程里，stdout 是协议通道（verify ⑫ 实测抓过
  "需嵌入 x/y 块"污染 JSON 输出的事故）。重建成功还会显式清 BM25 缓存：
  其版本号是库内条数，改内容不改条数时版本号不变，不能赌。
- **领域词典**（第 11 步，2026-10-06）：口语俗称 → 库内书面术语的手工对照表
  注入改写 prompt——"存笔记的东西"→向量数据库这类项目黑话通用模型猜不到
  （金标 2 问盲区实测救回且稳定第 1）。为什么手工策展而不是从库自动抽词：
  自动抽高频词会抽到"怎么做/笔记"这类无区分度的词反而带偏；只收"通用模型
  猜不到 + 库里真实存在"的映射，个位数条目防膨胀。
- **词典维护三层**（第 13 步，2026-10-06）：
  内置（`REWRITE_GLOSSARY`，只读）+ 本地（`glossary.local.txt`，人审过的词条，
  **热生效**——mtime 版本号机制与 BM25 缓存同款，长驻 MCP server 不用重启）+
  候选池（`glossary.cand.txt`，检索自动沉淀的"改写致胜对"）。维护命令见
  `glossary.py`（list / add / rm / cand / promote / drop）。
  **候选为什么不自动进 prompt**：改写致胜对（原问句过闸失败、强相关结果由
  变体捞回）是"换词成功"的实证，但变体措辞是模型泛化的，自动注入等于把
  脏词条写进每次检索——沉淀只记证据，提升必须人审。
- **改写闸 REWRITE_GATE=0.60**（第 11 步实测返工）：原问句先给主干候选精排，
  top1 分数够高 = 原问句已稳稳命中，变体不参与精排——否则词典会把变体拽向
  跑偏主题（实测："MCP 服务器端怎么开发"被套上"多智能体协作/ACP"变体，
  正主在召回第 2 却被挤出前 5）。校准数据（仅原问句精排 top1）：必须放行
  变体的口语题 0.58 / 0.03，必须挡住变体的书面题 0.64——0.60 是窄缝，如实
  记录为已知脆弱点，靠金标盯防。
- **单篇多样性 MAX_PER_NOTE=2**（第 11 步实测）：top_k 里同一篇笔记最多 2 块
  ——"查笔记"要的是命中的**笔记清单**，不是同一篇的 5 个段落；两簇都相关的
  问句（"AI记性不好"）不会被高分簇整簇挤掉另一簇。
- **范围限定 scope / `--in`**（第 14 步，2026-10-07）：把检索圈在一条**路径前缀**里
  （`--in "11-实践案例"`，或细到 `--in "2-Agent能力/提示词缓存.md"`）。判据只此一处
  （`query._in_scope`），**向量与 BM25 两条通道共用同一个口径**——"范围"只有一个
  定义，不会两条通道各筛各的。三处刻意的选择：**路径段级**匹配（`1-A` 不吞
  `1-Agent理论`）、尾斜杠先剥再拼（`"11-实践案例"` 与 `"11-实践案例/"` 同结果）、
  `None`/空 = 不限（缺省行为与加参数前逐位一致）。两条语义边界必须说清：
  ① 带范围时召回条数放大到 `SCOPE_RECALL_K=200` —— 向量与 BM25 都没有"前缀过滤"
  的原生支持，只能多召回再筛，不放大就会出现"范围内明明有、只是排在 20 名之外"的
  **假空结果**（粗排 200 条仍是毫秒级）；② **范围内无命中就返回空**，回执里回显
  `scope` 并明说"限定范围不会自动退回全库"——"范围写错了"与"库里真没有"必须是两种
  回执，否则人会把前者误读成后者。
  **为什么不做"精确行号引用"**：先试过"命中块 → 源文件第 N 行"的回链，实测把 120 条
  命中块的正文回源文件里逐字找，**只有 1 条（0.8%）对得上**——分块是
  `MarkdownHeaderTextSplitter` 的产物，空白与标题处理跟原文件不一致，硬做等于 99%
  的偏移默默算错；宁可要"范围限定"这条**确定性**的路（前缀判据是纯函数、没有概率成分）。
- **为什么要双通道**（2026-10-06 grep 真值对照实测）：`hit@5` / `HNSW` / `TTL`
  这类精确标识符查询在纯向量通道 3/5 脱靶——双塔只认"意思相近"，不认"字面相同"；
  BM25 补字面那一半后三项全部进第 1。分词：ASCII 词元整体保留（`cache_control`、
  `json.dumps` 不拆散）+ 中文二元组，免 jieba 依赖；BM25 索引从 Chroma 惰性构建、
  常驻内存，以库内条数为版本号自动随增量重建刷新。
- 嵌入是"双塔"（各自编码算距离，快但粗）；reranker 是 cross-encoder
  （query+doc 拼一起过模型，慢但准）——所以只对融合后的候选池精排
  （主干前 12 + 变体新块前 12）。
- 分数口径：精排生效 = reranker 相关度（0~1，>0.5 强相关）；降级 = 1 − 余弦距离。
  每条结果同时带 `cosine` 字段，召回侧可解释性不丢（BM25 独有命中块会补算余弦）。
- 摘要按句边界截断（`_snippet`）：宁可短半句，不留半句话；无句界才保底硬切。
- 编码：侧车输出强制 UTF-8（query.py reconfigure + flint 传 PYTHONUTF8=1 双保险）。
  Windows 默认 GBK 编不了笔记里的 emoji，2026-10-06 实战炸过两次，verify ⑤ 已钉。

## 金标评测（eval.py）

29 问（18 语义类 + 3 精确标识符类 + 8 口语化类）× 两模式对照：

| 模式 | hit@5 | MRR |
|---|---|---|
| 混合召回（对照组） | 79.3% | 0.690 |
| 混合+精排 | **96.6%** | **0.822** |

跑分口径（2026-10-06 补，**可复现**）：base 对照组全程无 LLM 参与，跑 1 次即可；
实验组的改写有抽样随机性，每问跑 `RAG_EVAL_ROUNDS`（默认 3）轮取**众数投票**——
过半轮次命中才算命中、排名取命中轮中位数，单轮抽样运气不再决定分数
（29 问 × 3 轮 ≈ 6 分钟；`RAG_EVAL_ROUNDS=1` 退回单轮口径，verify ⑪e 钉住投票逻辑）。

其中口语化 8 问是查询改写的专项考题：无改写诊断 3/8 → 有改写 7/8
（领域词典把 2 问改写器常识盲区救回且稳定第 1）；语义类 18 问 + 标识符类
3 问保持 100%（"补充不稀释"+改写闸保证书面零回归）。
剩 1 问（"AI记性不好怎么办"）为**多簇答案边界题**：知识笔记与实践案例日志
两簇都相关，3 轮投票 0/3 —— 不是抽样运气能救的，继续砸成本收益递减，如实记录收工。

- 标识符类期望路径来自 grep 全库扫描的真值，不是拍脑袋；查询词刻意换说法
  （语义类）或就是字面 token（标识符类）。
- 踩过的评测坑：金标第一版给"Agent 之间怎么互相通信协作"只标了 ACP协议.md，
  但 多Agent协作.md 的通信方式一节同样是正确答案——**单期望标签会把"检索对了"
  错判成"没命中"**，已改为多正确答案（元组任一命中即算）。
- 精排的可见收益：最差个案从第 5 名提到第 1（MCP-Server）；分数判别度远高于
  余弦（相关 0.99 vs 无关 0.00x），下游"多相关才算相关"的阈值判断更可靠。

## MCP 通道（flint 的正式调用路径）

- 协议：MCP stdio 传输 = newline-delimited JSON-RPC 2.0，日志只走 stderr 不污染协议流。
- server 端纪律：未 initialize 的请求按规范 -32002 拒绝；tools/call 的重依赖
  （chromadb/openai）**惰性加载**——tools/list 这类轻请求在索引库损坏时依然可用；
  检索失败按 `isError:true` 回报，不吞成协议错误。
- client 端纪律（src/mcp/client.ts）：长驻连接（握手一次、tools/call 按 id 配对复用）、
  超时即杀连接（迟到响应会让 id 错位）、进程死亡下次调用自愈重启。
- note_search 双通道：MCP 主路径失败 → 自动降级回一把一 spawn（query.py --json），
  协议层单点故障不拖垮工具可用性。
- 手动验协议（无需 flint）：

```bash
printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{}}' \
  '{"jsonrpc":"2.0","method":"notifications/initialized"}' \
  '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"note_search","arguments":{"query":"提示词缓存","top_k":3}}}' \
  | PYTHONUTF8=1 .venv/Scripts/python.exe mcp_server.py
```

## 索引更新（增量，2026-10-06 起）

```bash
.venv/Scripts/python index_build.py          # 增量：只处理改过/新增/删除的篇目
.venv/Scripts/python index_build.py --check  # 干跑：只报告差异，索引不动
.venv/Scripts/python index_build.py --full   # 强制全量重建（换模型/换口径后用）
```

- **机制**：`build-state.json` 记录每篇的 (mtime, size) 签名；变更篇目先按 path
  删净旧块再插新块，未变篇目零写入（块 id = 嵌入文本 sha256，内容不变 id 不变）。
- **孤儿块问题**：upsert 只加不删——笔记改了，旧版本块会永远留在库里，
  改过的笔记检索出旧内容、删掉的文件还能搜到。增量路径的"先删后插"是
  **正确性修复**，不只是提速；`--full` 也会顺手清一遍历史孤儿。
- 零变更运行快速退出，连 Chroma 都不开（sqlite 簿记都会动字节，账本纪律）。
- **自动重建**（2026-10-06 起）：日常不必手动跑——检索前发现过期会自动代劳
  增量重建（上面检索管线第一步）；手动跑本命令依然有效，两边共用
  `incremental_rebuild()` 同一段核心，不存在行为分叉。
- 测试隔离：`RAG_VAULT` / `RAG_INDEX_DIR` / `RAG_MANIFEST` 三个环境变量可把
  全套路径指到临时目录（verify-rag-index 套件的夹具就是这么做的）。
